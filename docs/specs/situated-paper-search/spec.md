# 상황 질문으로 논문 찾아 카드로 남기기

## 사용자 결과

동형암호 연구자가 지금 하려는 일을 문장으로 적으면, 그 일과 관련된 최신 논문을 한국어 카드로 받고, 그 카드가 노트에 남아 나중에 다시 꺼내 볼 수 있습니다.

검색 키워드를 고를 필요가 없습니다. "DLLM을 동형암호로 구현하려는데, diffusion 구조에 동형암호를 적용한 논문이 있어?"처럼 상황을 그대로 적으면 됩니다.

## 승인된 범위

상황 질문 입력부터 카드가 노트에 쌓이는 것까지 한 줄기를 완성합니다. 수집 소스는 arXiv 한 곳이고, 수집 시점은 질문을 던진 그 자리입니다.

`PRODUCT.md`의 핵심 루프 5단계 중 2~5단계를 얇게 관통합니다. 1단계(주기적 축적)는 다음 작업 단위입니다.

## 수용 기준

1. 상황 질문을 입력해 실행하면 관련 논문 카드가 나옵니다. 각 카드에는 제목, 저자, 발표일, 출처, 핵심 기여, 장단점, **이 질문에 적용할 수 있는 부분**, 원문 링크, 선정 근거가 한국어로 들어 있습니다.
   - 확인: "DLLM을 동형암호로 구현하려는데, diffusion 구조에 동형암호를 적용한 논문이 있어?"를 넣으면 *Privacy-Preserving Diffusion Model Using Homomorphic Encryption*이 카드에 포함됩니다.
2. 관련 논문이 적으면 적게 나오고, 없으면 없다고 말합니다. 정해진 개수를 채우려고 관련 없는 논문을 넣지 않습니다.
   - 확인: 동형암호와 무관한 질문을 넣으면 카드가 0건이고 그 사실이 화면에 드러납니다.
3. 어떤 검색 질의로 찾았는지가 결과에 드러납니다. 사용자가 검색 범위를 직접 판단할 수 있어야 합니다.
4. 카드는 노트에 저장됩니다. 질문 화면을 떠났다가 돌아오거나 새로고침해도 노트에 그대로 있습니다.
   - 노트의 카드는 접혀 있고 제목을 눌러 펼칩니다. 검색어와 질문으로 걸러낼 수 있습니다. 방금 찾은 결과 화면의 카드는 펼친 채로 둡니다.
5. 같은 논문이 다른 질문에서 다시 선정되어도 카드가 중복 생성되지 않습니다. 기존 카드에 그 질문의 적용 부분이 더해집니다.
6. 학회·저널 정보는 arXiv 메타데이터에 있을 때만 표시하고, 없으면 preprint로 표시합니다. 등급을 추측하지 않습니다. 발표 연도는 출처 표기와 나란히 강조해, 최신 연구인지 한눈에 보이게 합니다.
7. 진행 중, 빈 상태, 오류 상태가 정상 화면과 같은 구성으로 드러납니다.

## 확정된 제약과 근거

- **수집 소스는 arXiv API 한 곳입니다.** 실제로 확인한 결과 `abs:"homomorphic encryption"` 기준으로 당일·전일 논문까지 올라오고, LLM·비선형 근사·diffusion 질의 모두 관련 논문을 돌려줍니다. IACR ePrint는 검색이 HTML만 반환해 파싱 비용이 들어 이번 범위에서 제외합니다.
- **상황 질문 하나에서 검색 질의를 여러 개 만들어 결과를 합칩니다.** 단일 질의로는 범위가 좁을 때 놓칩니다. 검증에서 diffusion 질의는 2건만 나왔습니다.
- **선정 근거를 댈 수 없는 논문은 카드로 만들지 않습니다.** `PRODUCT.md`의 "근거 없는 답을 하지 않는다"를 이 작업 단위에서 구현하는 형태입니다. AI 채팅과 갈리는 지점이기도 합니다.
- **읽기는 한국어, 용어는 원문 표기를 유지합니다.** 원 논문을 찾아갈 수 있어야 합니다.
- **노트는 훑어보는 층과 읽는 층을 나눕니다.** 카드가 쌓이면 전부 펼쳐진 목록은 훑어볼 수가 없습니다. 25건 기준으로 화면 20개 분량이던 것이 접은 뒤 4.3개로 줄었습니다. 내용은 하나도 덜어내지 않고 접어둘 뿐입니다.
- **노트 저장은 화면 코드와 분리해 둡니다.** 필터가 클라이언트에서 돌아야 하는데 저장 코드가 같은 파일에 있으면 파일 시스템 모듈이 클라이언트 번들로 끌려가 빌드가 깨집니다.
- **선별과 카드 작성 모델은 Claude Haiku 4.5로 고정합니다.** 실행 검증에서 선별 품질이 충분해 더 비싼 모델을 쓸 이유가 없었고, 결제한 API 크레딧 안에서 비용을 예측 가능하게 두는 것이 사용자의 요구입니다. 환경변수로 바꾸는 통로를 두지 않아 실수로 비싼 모델이 걸리지 않게 합니다.
- **화면 구성은 [ui-composition 결정 계약](../../decisions/ui-composition.md)을 따릅니다.** 이 계약이 shadcn 조합, semantic token, 상태 표현, 레이아웃 shell 규칙을 지배합니다. 규칙 본문은 그 문서에 두고 여기서 되풀이하지 않습니다.

## 가정

되돌리기 쉬운 선택이라 확인 없이 정했습니다. 어긋나면 바꾸면 됩니다.

- 한 질문당 카드는 최대 5건까지 만듭니다. 그보다 관련 논문이 적으면 있는 만큼만 냅니다.
- 판단 근거는 arXiv 초록입니다. 전문은 읽지 않습니다.
- 생성된 검색 질의는 결과에 표시하되 사용자가 고쳐서 다시 돌리는 기능은 이번에 넣지 않습니다.
- 카드의 서지 정보는 arXiv 메타데이터를 그대로 씁니다.
- 카드의 "적용할 수 있는 부분"은 두 문장으로 씁니다. 첫 문장은 논문의 기법·구조·수치를 이름으로 지목하고, 둘째 문장은 질문자의 작업 어디에 들어가는지 또는 무엇부터 확인해야 하는지 밝힙니다. 한 문장 요약은 두루뭉술해 쓸모가 떨어진다는 사용자 검토 결과를 반영한 것입니다.

## 범위 밖

- **주 1회 자동 수집** — 노트에 쌓인 것이 없으면 자동 수집의 값어치를 확인할 수 없습니다. 이번 작업 단위가 카드를 만들어내야 그다음이 성립합니다.
- **검색 증강(RAG)과 임베딩 검색** — 학습 목표에 포함되지만 검색 대상이 될 코퍼스가 먼저 쌓여야 합니다.
- **IACR ePrint, 기업 연구 블로그** — 소스 확장은 한 줄기가 실제로 도는 것을 확인한 뒤입니다.
- **논문 전문 요약** — 초록으로 판단이 서지 않을 때의 동작이며, 초록 기반 선별이 쓸 만한지부터 확인합니다.
- **팀 공유와 사용자 구분** — 배포와 인증이 필요해 4시간 예산 밖입니다.
- **PoC item 탐색** — `PRODUCT.md`에서 이미 제품 범위 밖입니다.

## 유보한 지점

- **검색 증강(RAG) 도입 시점.** 노트에 카드가 쌓인 뒤 다음 작업 단위에서 정합니다. 그때까지는 arXiv 검색 결과를 LLM이 초록으로 선별하는 방식으로 동작합니다(잠정). 이 잠정 동작은 수용 기준 1·2에도 그대로 반영되어 있습니다.
- **팀 4명이 노트를 공유하는 방식.** 그때까지 노트는 사용자 구분 없이 한 곳에 쌓입니다(잠정). 카드의 "적용할 수 있는 부분"은 질문마다 붙으므로, 나중에 사용자 구분이 생겨도 이 구조는 유지됩니다.
- **자동 주기 수집의 트리거.** 주 1회를 기준 주기로 삼되 버튼인지 크론인지는 다음 작업 단위에서 정합니다.

## 남은 위험

- **검색 질의 생성 품질이 결과를 좌우합니다.** 질의가 빗나가면 관련 논문이 존재해도 찾지 못하고, 사용자는 그 사실을 알 수 없습니다. 수용 기준 3(질의 노출)이 이 위험을 일부 드러내지만 없애지는 못합니다.
- **초록만으로 판단하므로 오판이 생길 수 있습니다.** 사용자도 지금 요약만으로 핵심 아이디어가 안 잡히면 전문을 다시 넣는다고 했습니다.
- **Google Scholar를 쓰지 않아 저널 게재본과 citation 정보가 빠집니다.** 지금 쓰는 선별 기준(저명한 저자, citation)의 일부를 이번 버전은 제공하지 못합니다.
- **화면 프로토타입 없이 구현합니다.** 화면이 둘뿐이고 `ui-composition` 계약이 조합 규칙을 정하고 있어 생략했습니다. 카드의 정보 밀도와 배치가 첫 구현에서 어긋날 수 있으며, 실제 화면을 보고 조정합니다.
- **arXiv API 지연과 호출 제한.** 한 질문이 여러 질의를 던지므로 응답이 느려질 수 있습니다.
